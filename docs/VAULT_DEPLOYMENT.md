# Тестовый контейнер протокол-бота с AI Key Vault

## Назначение

Тестовый экземпляр бота работает в отдельном Docker-контейнере и получает ключи моделей у AI Key Vault. Токены провайдеров, `users.json`, IMAP-пароли и локальные кэши из рабочего экземпляра не переносятся.

## Поведение

- Каждый вызов нейросети проходит через Vault: запрос короткоживущей аренды ключа → проверка и расшифровка JWE в памяти → вызов выбранной модели.
- Запрос к основной модели `deepseek-chat` при ошибке переходит к OpenRouter `nvidia/nemotron-3-super-120b-a12b:free`.
- Для каждого вызова бот подписывает утверждение о Telegram-пользователе. Vault применяет отдельные права клиента и пользователя.
- Пользовательские ключи в настройках и legacy fallback в тестовом режиме выключены.
- В журнал пишутся корреляционный идентификатор, Telegram ID, задача, провайдер, модель, результат, HTTP-код и длительность; содержимое промптов и ключи не журналируются.
- Клиентский токен, ключ подписи JWT и закрытый ключ JWE уникальны для `protocols-bot-test`; Vault связывает события с отдельным `client_id`.
- Аудит Vault уже разделён по `client_id`, включая provider, модель, IP, пользователя и результат выдачи. Доступ самого бота к API агрегированной статистики оставлен выключенным.

## Настройки контейнера

`docker-compose.test.yml` создаёт `hunttech-protocols-bot-test`, подключает его к тестовой сети Vault с IP `172.22.0.10`, включает режим только для чтения, сбрасывает Linux capabilities и сохраняет данные бота и служебное состояние общей библиотеки в отдельных volumes. Секреты передаются Docker secrets; реальные файлы секретов и Telegram-токен не входят в Git или образ.

HTTP к Vault разрешён только для изолированного тестового профиля на внутренней Docker-сети. Для любого другого окружения клиент требует HTTPS и mutual TLS.

Тестовый сервер сейчас не имеет сетевого доступа к `api.telegram.org`: бот повторяет подключение с увеличивающейся паузой и не перезапускает контейнер. Проверочные обращения к Vault и модели выполняются из контейнера, но полноценный обмен сообщениями Telegram требует разрешить исходящий HTTPS к Bot API.

## Команды эксплуатации

Запуск/обновление:

```sh
docker-compose -f docker-compose.test.yml up -d --build
```

Проверка состояния и журналов:

```sh
docker inspect --format '{{.State.Status}}' hunttech-protocols-bot-test
docker logs --since 10m hunttech-protocols-bot-test
```

Проверка доступа через Telegram:

```text
/setup ai test
```

Успешная проверка подтверждает выдачу Vault lease, расшифровку JWE, вызов модели и ответ бота. В Vault audit должны появиться lease-запись и результат запроса с клиентом `protocols-bot-test`; секреты и тексты запросов не выводятся.

## Права Vault

Для тестового клиента должны быть зарегистрированы отдельные bearer-токен (в БД только PBKDF2 hash), издатель JWT с публичным ключом, публичный ключ JWE, разрешённый IP `172.22.0.10`, Telegram-пользователь администратора и отдельные grant-записи для `deepseek/deepseek-chat` и `openrouter/nvidia/nemotron-3-super-120b-a12b:free`, capability `chat.completions`. Не переиспользовать клиента HRM или другого бота.

Ключи аккаунтов DeepSeek/OpenRouter хранятся централизованно на стороне Vault. Текущая схема выбирает provider credential по провайдеру, а не по приложению; она не разделяет расходы в кабинетах самих провайдеров. Для такого разделения нужны отдельные ключи, выпущенные провайдерами, и поддержка назначения credential конкретному `client_id` в Vault.
