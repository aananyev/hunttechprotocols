# Протокол-бот: алгоритм и промпты для переноса в HRM HuntTech

Документ описывает, как устроен [@hunttech_protocols_bot](https://t.me/hunttech_protocols_bot),
и что именно нужно перенести, если тот же алгоритм требуется внутри HRM.

**Цель переноса:** по входному тексту расшифровки совещания получать структурированный
протокол по заданному шаблону, с корректным выбором шаблона по теме встречи.

Ссылки вида `bot.py:NNNN` указывают на строки исходника протокол-бота
(`~/StudioProjects/hunttechprotocols`).

---

## 1. Суть алгоритма

Алгоритм состоит из четырёх независимых частей. Каждая переносится отдельно и не
требует остальных.

| Часть | Суть | Объём в HRM |
|---|---|---|
| A. Разбор входа | письмо, вложение, фильтрация по теме | нужен, если источник — почта |
| B. Выбор шаблона | сопоставление темы с промптом по префиксу | **нужен в любом случае** |
| C. Генерация протокола | промпт + текст встречи → структурированный документ | **ядро, нужно в любом случае** |
| D. Публикация | две ветки, идемпотентность, иерархия папок | нужен, если результат идёт в Вики |

**Части B и C — это то, ради чего затевалась реализация в HRM.** Остальное — обвязка
вокруг Telegram и почты, в HRM она решается другими средствами.

## 3. Часть B. Выбор шаблона

Это самая переносимая и самая недооценённая часть. В протокол-боте реализована в
`wiki_route_section()` (`bot.py:1381-1395`):

```python
def wiki_route_section(user_id: int, display: str) -> str:
    wiki = get_wiki_config(user_id) or {}
    routing = wiki.get("routing") or {}
    disp_low = display.lower()
    for prefix, slug in routing.items():
        if disp_low.startswith(prefix.lower()):
            return slug
    return ""
```

### Три свойства, которые надо воспроизвести

**Сравнение по началу строки, без учёта регистра.** Не «содержит», не fuzzy-совпадение —
именно `startswith`. Иначе тема «Оперативка по Совете директоров» ошибочно попадёт
в подраздел «Совет директоров».

**Порядок обхода решает приоритет.** Возвращается первое совпадение. При пересечении
префиксов («Совет» и «Совет директоров») победит тот, кто раньше в словаре. Это
недостаток, а не достоинство: правила нужно делать непересекающимися либо сортировать
по длине префикса — от длинного к короткому.

**Нет совпадения — не ошибка.** Возвращается пустая строка, и дальше бот предлагает
выбор вручную (`bot.py:1543-1547`). Это правильное поведение: новая тема совещания
не должна ломать обработку.

### Конфигурация маршрутов

```json
"routing": {
  "Совет директоров":      "sovet-direktorov",
  "Оперативное совещание": "operativka",
  "Ретроспектива":         "retrospektiva"
}
```

В HRM это естественно ложится на справочник типов совещаний: у каждого типа есть
свой шаблон протокола и свой раздел хранения.

### Альтернатива: сопоставление по явному признаку

Если в HRM тема совещания уже структурирована (есть поле «тип совещания» в карточке
встречи), сопоставление по префиксу не нужно вовсе — достаточно точного совпадения
по типу. Совпадение по префиксу имеет смысл только там, где на вход приходит свободный
текст, как в протокол-боте.

## 4. Часть C. Генерация протокола

### 4.1 Форма вызова

```python
user_text = f"Тема: {display}\nДата: {date_str}\n\n{content}"
result = await call_ai(user_id, prompt_text, user_text,
                       system_prompt=None, progress=progress)
```

Принципы, которые стоит перенести как есть:

- **Промпт идёт в системное сообщение, текст встречи — в пользовательское.**
  Разделение снижает вероятность того, что модель начнёт «цитировать» инструкции
  в ответе.
- **Тема и дата передаются отдельными строками перед текстом.** Это не украшение:
  правило 2.1 промпта «Стандартное совещание» требует превращать относительные
  сроки («до пятницы») в календарные. Без явной даты снабжение не работает.
- **`temperature = 0.2`.** Протокол идёт в документооборот, разброс формулировок
  между двумя прогонами на одном конспекте недопустим.
- **`max_tokens = 4000`.** Длинный протокол Совета директоров в 8 блоков с
  приоритетами и заключением в это укладывается; 2000 обрежут.

### 4.2 Цепочка моделей

`call_ai()` (`bot.py:7638`) реализует три уровня деградации:

```
1. основная модель пользователя  (по умолчанию deepseek-v4-flash)
2. OPENROUTER_FALLBACK_MODEL     (nvidia/nemotron-3-super-120b-a12b:free)
3. OPENROUTER_FREE_MODELS       (цепочка бесплатных моделей по очереди)
```

Смысл: если основная модель недоступна или перегружена, обработка не теряется —
смысл протокола не зависит от конкретной модели. В HRM это даёт устойчивость при
пиковой нагрузке: совещания поступают пачками после рабочего дня.

### 4.3 Санитизация результата

Перед сохранением результат проходит `_sanitize_ai_md()` (`bot.py:55-73`) — нормализацию
Markdown. В HRM аналог обязателен: без нормализации страницы Вики накапливают
разнобой заголовков, лишние отступы и незакрытые блоки.

## 5. Промпты

### 5.1 Что в наборе

| Промпт | Где | Объём | Меняется пользователем |
|---|---|---|---|
| Промпт: ежедневный Совет Директоров | `prompts.json` | 1588 | да |
| Отправка кандидатов HUNTTECH | `prompts.json` | 1588 | да |
| Стандартное совещание | `prompts.json` | 4087 | да |
| Дайджест для группы | `bot.py:3802-3810` | 392 | нет |
| Краткий пересказ | `bot.py:3953-3960` | 384 | нет |

Первые три — пользовательские, их видно и правят через бота. Последние два зашиты
в код: это чистые функции сжатия готового протокола, их незачем выносить в настройки.

**Замечание по качеству набора.** Два из трёх пользовательских промптов — полные
копии друг друга (совпадающий SHA1 `4dff2796c7`), а третий обрывается на полуслове
и не содержит указаний на формат вывода. При переносе это важно: брать надо не всё,
а два достойных промпта, дописав третий.

### 5.2 Промпт «ежедневный Совет Директоров» — дословно

```
Ты — профессиональный секретарь Совета директоров IT-компании. Твоя задача — на основе
расшифровки встречи создать структурированное саммари в едином корпоративном формате.

СОСТАВ СОВЕТА ДИРЕКТОРОВ:
Генеральный директор
Директор по персоналу
Коммерческий директор
Директор по разработке

СТРУКТУРА САММАРИ:
ШАБЛОН ЗАГОЛОВКА:
Саммари ежедневной встречи Совета директоров [Название компании] Дата: [дата] Время: [время]

Участники:
[Имя] ([Должность]) [Имя] ([Должность]) [Имя] ([Должность]) — отсутствовал (если не было реплик)

ОСНОВНАЯ ЧАСТЬ:
Разделить на 6-8 ключевых блоков:
Операционные вопросы рекрутинга
Оптимизация рабочих процессов
Технические кадры
Развитие бизнеса
Коммерческая деятельность
Инфраструктура
Персонал
Маркетинг

Формат каждого блока:
Проблема/Задача: [суть вопроса]
Решение: [принятое решение]
Ответственный: [должность]
Срок: [конкретная дата]

ПРИОРИТЕТЫ:
Критические (до [дата]): [задача 1] [задача 2]
Среднесрочные (до [дата]): [задача 1] [задача 2]
Стратегические: [задача 1] [задача 2]

ЗАКЛЮЧЕНИЕ:
Следующая встреча Совета директоров: [дата], [время]:
состоится в следующий рабочий день утром в 9-00 МСК.
Документ утвержден для исполнения членами Совета директоров [Название компании]

СЛЕДУЮЩИЙ СОВЕТ ДИРЕКТОРОВ:
поручения, решения текущего совета директоров, на что обратить внимание на следующем совете

ТРЕБОВАНИЯ:
Определять присутствие по наличию реплик в расшифровке
Сохранять единую структуру для всех встреч
Указывать конкретные сроки и ответственных
Выделять приоритеты исполнения
Использовать профессиональный деловой стиль
```

**Что здесь хорошо и что переносить:**

*Сильные стороны:*

- Структура вывода задана явно, до уровня «Формат каждого блока» — модель не
  придумывает формат.
- Есть явный запрет на придумывание: присутствие определяется репликами, а не
  списком приглашённых.
- Приоритеты разделены на три горизонта с датами — это то, что потом используется
  при сверке исполнения.
- Требование «единая структура для всех встреч» делает протоколы сопоставимыми
  между итерациями.

*Ограничения, о которых стоит знать:*

- Тематические блоки жёстко заданы восемью пунктами. Для регулярного совещания это
  плюс, для разового — модель вынуждена выбирать пустые блоки или смешивать темы.
- Плейсхолдеры `[Название компании]`, `[дата]`, `[время]` ботом не подставляются.
  Если в HRM эти данные известны, их надо передавать в текст задания явно.
- Указание «следующая встреча состоится в следующий рабочий день в 9-00» — это
  факт, зашитый в промпт. Для конкретной организации его надо менять.

### 5.3 Промпт «Стандартное совещание» — ключевые части

Самый подробный промпт, и именно он лучше всего переносится: правила сформулированы
независимо от типа совещания.

**Начало:**

```
Ты — профессиональный корпоративный секретарь и аналитик ООО «ХантТек».

На основе полной расшифровки совещания необходимо подготовить структурированное
управленческое саммари, которое:
точно отражает содержание обсуждения;
фиксирует принятые решения;
выделяет поручения;
определяет ответственных;
фиксирует сроки;
показывает нерешенные вопросы;
позволяет на следующем совещании быстро проверить исполнение предыдущих договоренностей.

Саммари должно быть пригодно для использования руководителями компании как рабочий
управленческий документ.
```

**Раздел 1. ИСХОДНЫЕ ДАННЫЕ.** Описание того, что приходит на вход (расшифровка, дата
и время, название совещания, список приглашённых, дополнительный контекст, поручения
с предыдущего совещания), перечень 16 типов совещаний и ключевое указание:

```
Не привязывай структуру саммари жестко к типу совещания. Определяй необходимые
тематические блоки по фактическому содержанию расшифровки.
```

**Раздел 2. ОСНОВНЫЕ ПРИНЦИПЫ** — четыре правила, каждое переносится в HRM без
изменений.

*2.1. Не придумывать факты.*

```
Запрещено самостоятельно придумывать: решения, поручения, сроки, ответственных,
причины проблем, участников встречи, числовые данные, договорённости.

Если информация отсутствует — укажи явно: «Не определено на совещании».
```

Плюс нормализация относительных сроков: «завтра», «к пятнице», «до конца месяца»
превращаются в конкретную календарную дату, если дата совещания известна; иначе
исходная формулировка сохраняется.

*2.2. Отделять обсуждение от решения.*

```
Решением НЕ считаются: предложение, предположение, гипотеза, идея, спорное мнение,
вариант решения, намерение что-либо дополнительно проверить.

Решением считается только то, что участники фактически согласовали, либо то,
что руководитель явно поручил.
```

Это самое ценное правило в наборе. Без него протокол наполняется обсуждениями,
принятыми за решения, и перестаёт быть документом.

*2.3. Выделять поручения.* По возможности определить: что сделать, ожидаемый
результат, ответственного, срок, приоритет, зависимость от других задач.

*2.4. Определять присутствие по расшифровке.* Участник присутствовал, если у него
есть реплики. Упоминание человека другими участниками присутствием не считается.

**Разделы 3–5.** Формат заголовка (тема, тип, дата, время, продолжительность,
участники с пометкой об отсутствии); управленческое резюме из 3–7 пунктов в начале
документа; основная часть с самостоятельным делением на тематические блоки по
фактическому содержанию, список из 15 категорий.

**Дефект: содержимое обрывается на полуслове.** Файл заканчивается на слове `Маркетинг` —
это конец списка категорий. Разделов с форматом вывода, с поручениями списком и с
заключением нет.

Практическое следствие важно для переноса: **на этом промпте модель не задана
форма вывода вообще** — ни длины, ни обязательных разделов. Структура выводится
из дедукции, результат нестабилен между запусками. В HRM этот промпт обязательно надо
дописать разделом «ФОРМАТ ВЫВОДА» с указанием: сколько блоков, что в каждом,
в каком порядке, чем заканчивается документ.

### 5.4 Дайджест для группы — дословно

```
Ты — секретарь IT-компании HUNTTECH. Ниже — протокол встречи. Переработай его в КОРОТКИЙ
ДАЙДЖЕСТ для публикации в рабочей группе:
1) оставь только самое основное: решения, задачи, сроки, ответственные;
2) максимум 10 предложений;
3) используй корректное форматирование Markdown: заголовок, списки (- или 1.), жирный
   текст для ключевого;
4) без воды, вводных фраз и приветствий.
```

Применяется вторым шагом: сжатие уже готового протокола. Единственное числовое
ограничение — 10 предложений, и оно проверяемо.

### 5.5 Краткий пересказ — дословно

```
Ты — секретарь IT-компании HUNTTECH. По конспекту/стенограмме встречи составь КРАТКИЙ
КОНТЕКСТ ровно из 3 предложений:
1) о чём была встреча;
2) список участников;
3) самое важное решение или событие встречи.
Без заголовков, без нумерации, просто 3 коротких предложения.
```

Самая жёсткая спецификация: ровно три предложения, строго определённое содержание
каждого, прямой запрет на оформление. Единственный промпт, где форма вывода задана
полностью, — и как раз поэтому он самый предсказуемый.

## 6. Структура промптов в HRM

По протокол-боту видно, что промпты условно делятся на три вида, и в HRM их стоит
разделить так же.

| Вид | Что делает | Пример | Хранить в HRM |
|---|---|---|---|
| Шаблон протокола | превращает расшифровку в документ | Стандартное совещание, Совет директоров | да, в настройках типа совещания |
| Сжатие готового | отжимает протокол до дайджеста | Дайджест, Кратко | да, но как системные шаблоны |
| Тексты интерфейса | отвечает в чат | `/help`, подсказки | не через AI, обычный текст |

Третий вид в HRM лучше вообще убрать из AI: справку должен отдавать код, а не модель.
В протокол-боте тексты справки как раз зашиты в код (`bot.py:5149-5246`) — правильное
решение, его стоит перенести.

Хранение шаблонов: пользовательские промпты в протокол-боте лежат в `prompts.json`
и редактируются через бота. В HRM естественное место — карточка типа совещания
или справочник шаблонов протоколов с историей версий.

## 7. Что переносится в HRM, а что нет

### Переносится

**Выбор шаблона по типу встречи.** Механизм `wiki_route_section()` целиком. В HRM поверх
него — проверка прав доступа: не каждый сотрудник должен видеть протокол совета
директоров.

**Генерация протокола по шаблону.** Промпт в системное сообщение, текст встречи
в пользовательское, тема и дата отдельными строками, `temperature` 0.2.

**Мультифоллбэк моделей.** Три уровня деградации.

**Санитизация Markdown** перед сохранением.

**Правила 2.1–2.4** из промпта «Стандартное совещание» — дословно, они не привязаны
к Telegram.

**Сохранение оригинала рядом с результатом.** В HRM это особенно ценно: расшифровка
совещания хранится в карточке встречи, протокол — в карточке совещания, и всегда
видно, из чего он получен.

### Не переносится

**Часть A целиком.** IMAP, `BODY.PEEK[]`, `UID MOVE`, фоновый цикл каждые 5 минут,
`notified_comms.json`. В HRM источник совещания известен заранее — это запись
встречи, а не письмо в ящике. Вся обвязка не нужна.

**Кнопки и меню Telegram.** Состояния `WikiProgress`, `AddPromptState` и остальные
десять FSM-состояний — это про диалог, в HRM диалога нет.

**Промежуточные папки Вики.** `Конспекты/ГГГГ/ММ месяц/` создаётся потому, что
Вики не создаёт промежуточные страницы автоматически (`bot.py:1564-1576`). В HRM с
иерархией проблемы нет.

**Тексты справки.** Справка должна быть статичной.

**Короткий uid для callback.** Ограничение Telegram в 64 байта к HRM отношения не имеет.

## 8. Порядок реализации в HRM

### Шаг 1. Справочник шаблонов

Тип совещания → шаблон протокола. На старте два-три типа, покрывающих большинство
встреч. Начальный набор промптов: два достойных из протокол-бота, третий дописать
разделом «ФОРМАТ ВЫВОДА».

### Шаг 2. Поле «расшифровка» в карточке встречи

Текст совещания входит в карточку встречи. Дата встречи уже есть — именно её надо
передавать в задание, чтобы работала нормализация относительных сроков.

### Шаг 3. Генерация

Один вызов модели по шаблону типа совещания. `temperature` 0.2, `max_tokens` 4000.
Сверх этого — мультифоллбэк.

### Шаг 4. Сохранение

Результат в поле «протокол» карточки совещания, санитизированный. Расшифровка
остаётся в своём поле в неприкосновенном виде.

### Шаг 5. Разбор протокола на структуру

Это то, чего в протокол-боте нет, а в HRM нужно. Правило 2.3 промпта требует
выделять поручения с ответственными и сроками — но модель отдаёт это текстом.
Для HRM нужен второй шаг: разложить текст протокола на решения, задачи, ответственных
и сроки и положить их в поля сущностей.

Здесь важно не изобретать новое правило, а использовать уже работающее: в наборе
протокол-бота формат блока задан явно (`Проблема/Задача → Решение → Ответственный →
Срок`), значит разбирать такой текст предсказуемо. Отдельного промпта на разбор
не понадобится, если сохранять этот формат.

### Шаг 6. Проверка исполнения

Поле «выполнено» у задачи + дата сверки на следующем совещании. Это следует
из первой же строки промпта: «позволяет на следующем совещании быстро проверить
исполнение предыдущих договоренностей». В протокол-боте эта возможность
предусмотрена, но не реализована — в HRM это самое очевидное, что стоит добавить.

## 9. Грабли

**Пустой формат вывода даёт нестабильный результат.** Главная проблема промпта
«Стандартное совещание». Без явного раздела с форматом модель каждый раз придумывает
структуру заново, и протоколы перестают быть сопоставимыми.

**Два промпта с одинаковым текстом под разными именами** — в наборе протокол-бота
они есть. В HRM такое надо предотвратить на уровне справочника: уникальность
по содержимому, а не по названию.

**Сопоставление по префиксу хрупко.** «Оперативка по Совете директоров» не попадёт
в подраздел «Совет директоров». Если в HRM есть поле типа встречи — использовать
его, а не префиксы.

**Латентная ошибка в выборе промпта.** В протокол-боте весь блок выбора промпта
(`bot.py:1598-1632`) случайно оказался внутри `if progress:` из-за лишнего отступа
на строке 1598. Файл компилируется, все текущие вызовы проходят с непустым
`progress`, и дефект не проявляется. При переносе этот код писать заново — и
не тянуть в него структурную ошибку, которая не видна при проверке синтаксиса.

**Слишком низкий лимит ответа.** 4000 токенов хватает для протокола Совета директоров
в 8 блоков. Для протокола на 12 блоков потребуется больше — считать заранее,
сколько токенов даёт один блок, и закладывать с запасом.

**Очистка кэша.** `notes_cache.json` в протокол-боте дорос до 19 МБ, ротации нет.
В HRM это будет таблица протоколов — нужен архив по годам.

**Прокси с логином и паролем в коде** (`bot.py:7598`) — в HRM то же самое окажется
в конфигурации сервера. Учётные данные должны быть в настройках подключения.

## 10. Сводка

Для переноса в HRM нужны три вещи:

1. **Сопоставление типа встречи с шаблоном протокола** — механизм `wiki_route_section()`,
   в HRM поверх поля типа встречи и поверх проверки прав.

2. **Два промпта-шаблона** — «Совет директоров» с фиксированной структурой
   из восьми блоков и «Стандартное совещание» с четырьмя правилами
   («не придумывать», «отделять обсуждение от решения», «выделять поручения»,
   «присутствие по репликам»). Третий промпт из набора использовать нельзя —
   он обрезан.

3. **Два промпта сжатия** — дайджест до 10 предложений и краткий пересказ ровно
   из трёх. Оба работают как есть, оба проверяемы по числу предложений.

Плюс дисциплина вызова: промпт в системное сообщение, текст встречи и дата
в пользовательское, `temperature` 0.2, `max_tokens` 4000, мультифоллбэк моделей,
санитизация результата.

Не переносится ничего, что связано с почтой, Telegram-кнопками и иерархией папок Вики.
